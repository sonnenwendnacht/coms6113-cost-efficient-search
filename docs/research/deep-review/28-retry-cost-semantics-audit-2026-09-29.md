# Retry cost semantics audit (2026-09-29)

Research-only code audit. No experiment, replay, model call, or selector run
was launched for this note.

## What the current runner actually charges

The nine-model generator runs a complete row `(solver_1, solver_2, solver_3)`
on one MathQA question. Each reached attempt makes a solver call and then a
verifier call. The verifier prompt contains only the problem, options, and
candidate response; it explicitly says that the answer key is unavailable.
The answer key is consulted only after the workflow to compute the offline
`final_correct` field.

The retry loop stops as soon as the verifier returns `VERDICT: PASS`. If it
returns `RETRY`, the next solver prompt includes the previous output and
verifier feedback. Consequently, both the number of reached calls and the
input length of later calls depend on the observed path. The recorded cost is

```text
K(c,q) = sum over reached calls
         coefficient(model(call)) * input_tokens(call).
```

Output tokens are explicitly excluded, and provider-cache discounts are
disabled. The implementation is in
[`run_workflow`](../../../scripts/run_experiment1_nine_model.py) and
[`primary_cost`](../../../src/retry_search/experiment1.py). The metadata records
the output-token and cache settings, so a later analysis can distinguish this
proxy charge from an invoice.

## Why this matters for the literature boundary

If every attempt were always executed with a fixed input length, the row cost
would be a known deterministic quantity and generic cost-aware BO/BAI methods
would be much closer baselines. In the current protocol, `K(c,q)` is an
unknown-before-measurement, path-dependent value generated by the same
early-termination process that generates final correctness `Q(c,q)`. A
row-average cost or model coefficient alone can therefore mis-rank two actions:

* a cheap solver can trigger many long retries;
* a strong solver can terminate early, but its first prompt can be more
  expensive; or
* an outcome can change both final correctness and the later prompt length.

The local generator uses deterministic decoding (`do_sample=False`) and fixed
model snapshots. Conditional on a fixed question, row, and runner version,
`K(c,q)` is therefore deterministic, rather than a stochastic repeated-pull
cost. If deployment adds sampling or provider variability, it becomes a random
path cost and should be reported as a distribution. In the current trace, the
quality–cost coupling is across row/question cells and through the early-stop
path, not necessarily within repeated draws of one identical cell.

This is the narrow domain distinction from fixed arm-cost methods such as
PBGI/GittinsEval and from cost-aware dueling models whose cost is attached to
the selected arm pair. It is not a new generic cost-aware bandit theorem.

## Required ablation and reporting

The paper should report two cost regimes:

1. **Deterministic-cost control:** hold every attempt's input template and
   reach schedule fixed, or charge a registered row/question proxy independent
   of observed outcomes. This tests whether the proposed allocation helps even
   when only quality is retry-aware.
2. **Path-dependent cost setting:** use the actual reached-call ledger above,
   including retry feedback and input lengths. This tests the intended
   quality–cost coupling. If inference is repeated with stochastic model
   outputs, report the resulting cost distribution separately.

For each regime report actual search spend, number of complete cells/pairs,
cost distribution by row, and held-out quality of the frozen recommendation.
Do not call `coefficient_model * input_tokens` a known *cell cost* when the
input tokens or reached attempts are outcome-dependent; call the coefficient
known and the realized cell charge observed after execution.

## Safety and deployment distinction

The answer-key-scored `final_correct` value is an offline benchmark reward for
selector replay. The deployment verifier supplies only pass/retry control and
does not establish final correctness. A live search algorithm must either name
an allowed quality signal (for example, a judge or user label) or be described
as offline configuration search. Keeping `Q`, answer-key-blind `A`, and
realized charge `K` as separate fields prevents accidental leakage in the
method description.
